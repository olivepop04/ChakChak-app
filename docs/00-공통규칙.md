## 1. 하루 작업 흐름

### 시작할 때 — 항상 이 두 줄부터

```bash
git checkout dev && git pull origin dev
```

```bash
git checkout 내브랜치 && git merge dev
```

**이걸 건너뛰면 브랜치가 며칠 만에 뒤처집니다.** 그 상태로 일주일 작업하면 나중에 합칠 때 충돌이 수십 개 납니다. 초심자 팀에서 가장 자주 나는 사고입니다.

### 올리기 전에 — 반드시 확인

```bash
npm run build
```

**통과해야 올립니다.** 오류가 있는 코드가 `dev`에 들어가면 다음 사람이 전부 막힙니다.

### 올리기

```bash
git add -A && git commit -m "style: 액션 카드 여백 조정"
```

```bash
git push origin 내브랜치
```

터미널에 뜨는 링크로 PR을 만듭니다.

> ### ⚠️ PR 을 열면 **받는 쪽이 `main` 으로 자동 선택돼 있습니다**
>
> 이 저장소의 기본 브랜치가 `main` 이라, GitHub 이 PR 을 만들 때
> **자동으로 `main` 을 목표로 잡습니다.** 우리 규칙은 `dev` 인데도요.
>
> ```
> base: main  ←  ✗ 이대로 두면 안 됩니다
> base: dev   ←  ✓ 직접 바꿔주세요
> ```
>
> PR 화면 위쪽의 **`base: main` 을 눌러 `dev` 로 바꾸고 나서** 만드세요.
> 화살표 왼쪽이 받는 쪽, 오른쪽이 내 브랜치입니다.
>
> **그대로 두면** `main` 은 배포용이라 Vercel 이 바로 빌드합니다.
> 리뷰도 못 받은 코드가 배포 링크에 올라갑니다.
>
> 잘못 만들었으면 당황하지 마세요. **PR 을 닫고 다시 만들면 됩니다** —
> 아니면 같은 화면에서 base 만 `dev` 로 바꿔도 됩니다. 커밋은 그대로 남습니다.

> ### 초록색 "Compare & pull request" 배너는 눌러도 되나요
>
> 브랜치를 푸시하면 GitHub 이 저장소 위쪽에 초록 버튼을 띄웁니다.
> **그 버튼도 `main` 을 기본으로 잡습니다.** 눌러도 되지만
> **PR 을 만들기 전에 base 를 `dev` 로 바꿨는지** 반드시 확인하세요.
>
> 그리고 **올릴 작업이 없는데 배너가 뜨는 경우**도 있습니다
> (민호가 브랜치를 최신으로 맞춰주면 그렇습니다).
> 그때는 그냥 두시면 됩니다 — 며칠 지나면 사라집니다.

### 커밋 메시지

앞에 종류를 붙이고 한국어로 무엇을 했는지 씁니다.

| 앞머리 | 언제 |
|---|---|
| `feat:` | 새 기능 |
| `fix:` | 잘못된 것을 고침 |
| `style:` | 화면 모양만 바꿈 |
| `refactor:` | 동작은 같고 코드만 정리 |
| `docs:` | 문서만 |

## 2. 절대 하면 안 되는 것

| 금지 | 무슨 일이 생기나 |
|---|---|
| `main`에서 작업 · `main`에 직접 push | 실제 배포 브랜치라 곧바로 인터넷에 올라갑니다 |
| 상의 없이 `lib/` · `components/ui/` 수정 | 다섯 명이 동시에 쓰는 공유 구역입니다 |
| 화면에서 `supabase.from(...)` 직접 호출 | 같은 데이터가 화면마다 다르게 보이기 시작합니다 |
| `.env.local`을 git에 올리기 | 키가 공개됩니다 |
| 키를 카톡·디스코드로 전달 | 캡처가 남고 대화방은 검색됩니다 |
| Supabase 콘솔에서 테이블 직접 수정 | 다른 사람 DB와 달라집니다 |
| 남의 담당 폴더 수정 | 병합할 때 충돌이 납니다. 필요하면 먼저 말하세요 |

### 여러 구역에 걸친 변경은 한 사람이 전부 맡습니다 (2026-09-14)

> **스타일·문구·제목을 통일하는 일은 폴더로 나눠지지 않습니다.**
> 한 사람이 전부 맡고, 그동안 그 파일은 아무도 건드리지 않습니다. **한 PR 로 올립니다.**

폴더 담당은 「각자 자기 화면을 만든다」에는 잘 맞지만, **위치가 아니라 패턴을 따라가는 변경**에는
맞지 않습니다. 실제로 두 번 겪었습니다.

| 요청 | 걸친 범위 |
|---|---|
| 화면 제목 한글로 통일 | 4명 · 7파일 |
| 버튼 높이 고정 해제 (글자 200%) | 5명 · 21파일 |

번지는 이유는 **공통 컴포넌트를 거치지 않는 것**입니다. `Button.tsx` 를 쓰는 파일은 **15개**인데
`<button>` 을 직접 쓴 파일이 **27개**입니다 (2026-09-28 실측 · 9/22 에는 16 · 26 — 세는 기준은
`grep -rl "<button" app/ components/` 에서 `Button.tsx` 자신을 뺀 것).
새 화면을 만들 때는 **`components/ui/` 의 것을 먼저 찾아 쓰세요.** 없으면 만들자고 말해주세요 —
그 한 번이 다음 통일 작업의 21파일을 1파일로 줄입니다.

**입력칸 공통 컴포넌트가 생겼습니다** — `components/ui/Input.tsx` (2026-09-22, 소정님).
전에는 이것이 없어서 같은 `min-h-11 rounded-xl border border-neutral-300 px-4 py-3 text-[15px]`
이 16개 파일에 복사돼 있었습니다. 지금 4개 파일이 `Input` 을 씁니다(2026-09-28 — 9/25 에 `SharePanel` 이 빠짐). 손으로 적은 곳은 9/22 기준 12개였습니다.
**새로 만드는 입력칸은 손으로 짜지 말고 `Input` 을 쓰세요.** 남은 12개는 손대는 화면이
생길 때 하나씩 옮기면 됩니다 — 그것만으로 다음 타이포·높이 통일 작업이 1파일이 됩니다.
같은 PR 로 `Chip` 에 `size="sm"` 이, `Button` 에 `href`(링크로 렌더) 가 들어왔고
`tailwind.config.ts` 에 `brand` · `danger` · `warning` · `info` 토큰이 생겼습니다.
대괄호로 색을 적던 곳(`bg-[#00A56E]` 등)은 이제 토큰을 쓸 수 있습니다.

절차는 이렇게 합니다.

1. **시작 전에 민호에게 알립니다.** 어떤 파일을 건드릴지 목록으로 주세요.
2. 민호가 공지하고, 그 기간에는 **다른 사람이 그 파일을 건드리지 않습니다.**
3. **파일별로 쪼개 나눠 고치지 마세요.** 세 명이 나누면 같은 패턴이 세 가지로 갈립니다.
4. 한 PR 로 올리면 민호가 점검하고 병합합니다.

**「미리 알려야 하는 것」 을 두 가지로 좁혔습니다** (2026-09-22, 소정님 제안).

화면을 만들다 보면 남의 구역 파일 몇 개를 스치는 일은 계속 생깁니다. 그때마다 공지하면

단 **로직·백엔드를 안 건드리는 선까지**입니다.

`input`·`button` 을 공통 컴포넌트로 바꾼 것이라, **규칙대로 한 사람이 한 PR** 로 올라왔고

**`components/ui/` · `components/layout/` · `lib/` 은 공유 구역입니다.** 고칠 때는 먼저 말해주세요.
`components/layout/Header.tsx` 는 **22개 화면이 씁니다** (2026-09-28 — 참여 완료 화면이 빠짐) — 다섯 담당 전원의 구역에 걸칩니다.

## 4. 데이터를 다루는 방법

> **읽기는 `lib/queries/`, 쓰기는 `lib/mutations.ts`.**

각자 쿼리를 짜면 조건을 다르게 걸어서 **같은 데이터가 화면마다 다르게 보입니다.** 나간 사람을 빼는 걸 잊거나, 상태 필터를 놓치는 식으로요.

```tsx
// ✅ 이렇게
const actions = await getActionFeed(supabase, { viewerId: user?.id ?? null });

// ❌ 이러지 마세요
const { data } = await supabase.from('actions').select('*');
```

쓰기 함수는 **성공/실패와 한국어 메시지**를 돌려줍니다. `try/catch`가 필요 없습니다.

```tsx
const res = await joinAction(supabase, actionId, items);
if (!res.ok) { setError(res.message); return; }   // 그대로 화면에 표시
```

**필요한 함수가 없으면 직접 추가하지 말고 민호에게 요청하세요.**

> 함수 목록은 [CLAUDE.md](../CLAUDE.md)에 있습니다.

## 5. 화면을 만들 때 지킬 것

### 서버 컴포넌트가 기본입니다

`'use client'`는 **아래가 필요할 때만** 파일 맨 위에 씁니다.

- `useState` · `useEffect` 같은 훅
- `onClick` · `onChange` 같은 이벤트
- `window` · `localStorage`

데이터를 불러와 보여주기만 하는 화면은 서버 컴포넌트로 두고, **버튼만 떼어내서** 클라이언트 컴포넌트로 만드는 게 빠릅니다.

### 빈 상태를 반드시 넣으세요

목록이 비었을 때 아무것도 없으면 사용자가 막힙니다. **다음에 할 행동을 함께** 주세요.

```tsx
import { EmptyState } from '@/components/ui/EmptyState';

<EmptyState
  icon="🌱"
  title="아직 참여한 액션이 없어요"
  description="마음에 드는 액션을 찾아보세요."
  action={{ label: '액션 찾아보기', href: '/discover' }}
/>
```

### 문구를 직접 적지 마세요

```tsx
// ✅
import { ACTION_STATUS_LABEL } from '@/lib/constants';
{ACTION_STATUS_LABEL[action.status]}      // '모집 중'

// ❌ 사람마다 다르게 적게 됩니다
{action.status === 'ACTIVE' ? '모집중' : '...'}
```

카테고리 · 상태 · 시간 · 성별 문구는 전부 `lib/constants/index.ts`에 있습니다.

### 공통 컴포넌트를 쓰세요

비슷한 걸 새로 만들면 화면마다 버튼 모양이 달라집니다.

```
Button · Badge · Chip · EmptyState · Toast · Avatar
ActionCard · ImageUploader · RegionPicker · UserList
QuotaProgress
```

## 7. AI에게 코드를 시킬 때

**이 형식으로 물어보면 결과가 훨씬 정확합니다.**

```
@CLAUDE.md @docs/03-디자인-ui.md 를 읽고,
액션 카드(components/ui/ActionCard.tsx)의 디자인을 다듬어줘.

지켜야 할 것:
- props 이름과 개수는 바꾸지 않는다 (**여덟 화면**이 이 컴포넌트를 쓴다 — 홈 · Activity ·
  Discover · 내 프로필 · 저장한 액션 · 남의 프로필 · 남이 만든 목록 · 남이 참여한 목록)
- 새 supabase 쿼리를 만들지 않는다
- 문구는 lib/constants 에서 가져온다
- params 는 Promise 이므로 await 한다
```

**핵심은 "새로 만들지 말고 있는 걸 쓰라"고 못 박는 것입니다.** 이 말이 없으면 AI가 매번 자기 방식으로 코드를 새로 짜서, 사람마다 다른 코드가 나옵니다.

받은 코드는 **6번 체크리스트를 직접 돌려보세요.** AI가 만든 코드도 실행해보기 전에는 모릅니다.
