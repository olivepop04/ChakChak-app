## 0주차 — 세팅 (다른 사람이 기다리고 있음)

### 1. Supabase 프로젝트

1. [supabase.com](https://supabase.com) → New project → **Region은 Northeast Asia (Seoul)**
2. 비밀번호는 따로 안전한 곳에 저장 (다시 볼 수 없습니다)
3. Settings → API 에서 `Project URL`, `anon public`, `service_role` 복사
4. Settings → Team 에서 조원 4명 초대

### 2. SQL 실행 (순서 중요)

SQL Editor에서 **한 파일씩 통째로** 붙여넣고 Run.

```
supabase/01_schema.sql     테이블 15개 + 뷰 2개 + 트리거
supabase/02_rls.sql        RLS 정책 + Storage 버킷
supabase/03_functions.sql  RPC 함수 9개
```

**확인 방법**

- Table Editor에 `actions`, `action_items` 등이 보이는가
- Database → Functions 에 `join_action` 이 있는가
- Storage에 `action-images`, `result-images` 버킷이 있는가

오류가 나면 **어느 파일 몇 번째 줄인지** 메시지에 나옵니다. 앞 파일이 실패했는데 다음 파일을 실행하면 연쇄로 실패하니, 하나씩 성공을 확인하고 넘어가세요.

### 3. 타입 파일 교체

> `Database['public']['Tables']['profiles']['Row']` 형태로 바꾸거나, 별칭을 따로 만들어 주세요.

## 1주차 — 알림 6종

### 알림이 만들어지는 지점

**대부분 이미 DB 함수 안에 들어 있습니다.** 새로 만들 게 많지 않습니다.

| 알림 | 언제 | 어디서 만들어지나 | 상태 |
|---|---|---|---|
| `RESULT_REQUEST` | 활동 종료 → ENDED | `sync_action_status()` | ✅ 완료 |
| `RESULT_PUBLISHED` | 결과 공개 | `complete_action()` | ✅ 완료 |
| `CANCELLED` | 액션 취소 | `cancel_action()` | ✅ 완료 |
| `INVITED` | 공유하기 | `notify_invite()` | ✅ 완료 |
| `SCHEDULE` | 활동 전날 | **직접 만들어야 함** | ⬜ |
| `VOICE_REQUEST` | 완료 + 5일, 소감 미작성 | **직접 만들어야 함** | ⬜ |

### 남은 2종 — lazy 방식

서버가 정해진 시간에 도는 게 아니라, **사용자가 화면을 열 때 조건을 확인해서 만드는** 방식입니다.

`supabase/05_lazy_notifications.sql` 파일을 새로 만들어 함수를 추가하세요.

```sql
-- 활동 전날이면 SCHEDULE 알림을 만든다. 알림 화면을 열 때 호출한다.
CREATE OR REPLACE FUNCTION sync_my_notifications()
RETURNS VOID
LANGUAGE plpgsql SECURITY DEFINER SET search_path = public AS $$
DECLARE
  v_uid UUID := auth.uid();
BEGIN
  IF v_uid IS NULL THEN RETURN; END IF;

  -- 1) 내일 시작하는 액션 → SCHEDULE
  INSERT INTO notifications (user_id, type, action_id, event_key)
  SELECT v_uid, 'SCHEDULE', a.id, 'SCHEDULE:' || a.id || ':' || v_uid
  FROM actions a
  JOIN participations p ON p.action_id = a.id
  WHERE p.user_id = v_uid
    AND p.status = 'BEFORE_ACTION'
    AND a.status = 'ACTIVE'
    AND a.activity_start_at BETWEEN now() AND now() + interval '1 day'
  ON CONFLICT (event_key) DO NOTHING;

  -- 2) 완료 후 5일이 지났는데 소감을 안 쓴 액션 → VOICE_REQUEST
  INSERT INTO notifications (user_id, type, action_id, event_key)
  SELECT v_uid, 'VOICE_REQUEST', a.id, 'VOICE_REQUEST:' || a.id || ':' || v_uid
  FROM actions a
  JOIN participations p ON p.action_id = a.id
  WHERE p.user_id = v_uid
    AND p.status = 'AFTER_ACTION'
    AND a.status = 'COMPLETED'
    AND a.activity_end_at < now() - interval '5 days'
  ON CONFLICT (event_key) DO NOTHING;
END $$;

GRANT EXECUTE ON FUNCTION sync_my_notifications() TO authenticated;
```

`event_key`가 UNIQUE라 **같은 알림이 두 번 만들어지지 않습니다.** 여러 번 호출해도 안전합니다.

> **데모 주의:** lazy 방식이라 사용자가 안 들어오면 알림이 안 생깁니다.
> 발표 전에 시연 계정으로 알림 화면을 한 번 열어서 알림을 만들어 두세요.

### 알림 화면 — `/notifications`

**파일:** `app/notifications/page.tsx`

### 모집 항목 입력 UI — 가장 중요

라디오 2개로 받습니다.

```
몇 명이 필요한가요?
  ○ 정해진 인원이 필요해요     → 최소 [  ]명, 최대 [  ]명
  ○ 최소 인원만 필요해요       → 최소 [  ]명
```

저장 규칙:

| 사용자 선택 | target_type | min_required | max_allowed |
|---|---|---|---|
| 정해진 인원, 3~3 | `RANGE` | 3 | 3 |
| 정해진 인원, 3~5 | `RANGE` | 3 | 5 |
| 최소 인원, 10 | `MINIMUM` | 10 | `null` |

항목마다 추가로 받는 것:

- **성별 제한** — 남성만 / 여성만 / 누구나 (기본 누구나)
- **조건** — 조건명(`condition_name`) + 설명(`condition_desc`), 선택 입력
- **물품이면** 단위(`unit`) 자유 입력. 사람이면 `'명'` 고정

### 저장 흐름

```
[저장하기] → status='DRAFT' 로 insert/update. 검수 없음.

[공개하기] → 1) 코드가 필수값 확인 (제목·날짜·이미지·항목 1개 이상)
            2) POST /api/ai/review 호출 → PASS / REVISE / BLOCK
            3) 결과를 Owner에게 보여줌
            4) BLOCK 이면 공개 버튼 비활성
               REVISE 면 "그래도 공개하기" 허용
            5) Owner가 [최종 공개] 클릭 → publishAction() RPC
            6) 성공하면 POST /api/ai/classify 로 색인 생성
```

**AI가 PASS해도 자동으로 공개되지 않습니다.** 반드시 Owner가 버튼을 눌러야 합니다.

### AI 검수 API

**파일:** `app/api/ai/review/route.ts`

```ts
import { callStructuredAI, ReviewSchema } from '@/lib/openai';

const result = await callStructuredAI({
  agent: 'REVIEW',
  promptVersion: 'review-v1',
  system: `당신은 사회공헌 활동 플랫폼의 콘텐츠 검수자입니다.
아래 항목을 확인하고 JSON으로만 답하세요.
- 개인정보(전화번호·이메일·주민번호·계좌번호)가 본문에 노출됐는가
- 활동 설명이 참여자가 이해할 만큼 구체적인가
- 모집 취지가 사회공헌 활동에 맞는가 (영리·홍보·정치·종교 권유는 BLOCK)
- 차별적이거나 불쾌감을 주는 표현이 있는가

decision 기준:
  BLOCK  - 개인정보 노출, 명백한 영리·홍보, 차별 표현
  REVISE - 설명이 모호하거나 참여 방법이 불분명함
  PASS   - 큰 문제 없음

형식: {"decision":"PASS|REVISE|BLOCK","hard_errors":[],"warnings":[],"suggestions":[],"questions":[]}`,
  user: JSON.stringify({ title, description, category, items }),
  schema: ReviewSchema,
  actionId,
  userId,
});
```

`callStructuredAI`가 **Zod 검증·1회 재시도·`ai_runs` 로깅**을 다 처리합니다.

> **발표 준비:** `ai_runs` 테이블에 프롬프트 버전별 결과가 쌓입니다.
> 처음 프롬프트가 오탐을 낸 사례 → 프롬프트 수정 → 개선된 사례를 뽑으면
> 발표의 "검증·개선" 항목 근거가 됩니다. **초기 버전을 지우지 말고 `review-v1`, `review-v2`로 남겨두세요.**
